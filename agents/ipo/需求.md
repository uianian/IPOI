### 1.1.2 技术选型决策

| 决策项 | 选型 | 决策依据 |
|--------|------|----------|
| 编排骨架 | LangGraph | 原生支持状态图、条件路由、循环边，适合多Agent协作与辩论轮次控制；社区活跃，与LangChain生态兼容 |
| 辩论协议 | 自研 | LangGraph无内置辩论机制，需自研冲突检测、辩论调度、终止判定逻辑 |
| 跨模态融合 | 自研 | 招股书文本特征(低频静态)与市场时序特征(高频动态)的融合无现成方案，需自研特征对齐与加权融合策略 |
| Skill接口 | 自研 | 需要统一的Skill注册/发现/版本管理机制，LangGraph原生Tool不满足可追踪与版本兼容要求 |
| LLM推理后端 | vLLM | 高吞吐量推理，支持连续批处理与PagedAttention，满足3份招股书并发分析性能要求 |
| 向量检索 | FAISS + Chroma | FAISS用于高性能相似度检索，Chroma提供元数据过滤与持久化存储 |
| PDF解析 | PyMuPDF + Unstructured | PyMuPDF提取文本与页面映射，Unstructured处理复杂排版与表格 |
| 开发语言 | Python | 用户偏好，与PyTorch/Megatron/vLLM生态一致 |

## **1.3 实现设计文档**

### 1.3.1 MasterOrchestrator 总控决策Agent

**设计要点**：

1. **任务分解策略**：基于LangGraph的`add_node`注册任务分解节点，将用户尽调请求拆解为法务/财务/情绪三个并行子任务，设定优先级（法务=财务>情绪）与依赖关系（无前序依赖，并行启动）

2. **条件路由**：利用LangGraph的`add_conditional_edges`实现：
   - 分析完成后的冲突检测路由：`has_conflict → debate_round | cross_modal_fusion`
   - 辩论完成后的终止判定路由：`debate_resolved → cross_modal_fusion | debate_round(继续) | 不可调和冲突标记`

3. **冲突检测算法**：
   - 语义冲突：法务合规判定与财务风险评估的矛盾（如法务标记"关联交易合规"而财务标记"关联销售占比畸高"）
   - 背离冲突：市场情绪与基本面风险的背离（如基本面"高风险"但情绪"极热"）
   - 冲突检测基于预定义的冲突规则表与LLM辅助判断相结合

4. **辩论调度**：通过LangGraph的循环边（`add_edge`从辩论节点回到自身）实现最多3轮辩论，每轮将冲突描述发送给相关Agent补充证据或修正结论

5. **跨模态融合**：将招股书基本面特征向量与市场情绪特征向量进行加权融合，输出综合五级风险评级

### 1.3.2 LegalAgent 法务合规Agent

**设计要点**：

1. **分析流程**：
   - 第一步：调用`LongDocRetrievalSkill.retrieve()`检索法律相关段落（诉讼、行政处罚、知识产权、VIE架构等关键词）
   - 第二步：调用vLLM进行法律风险特征抽取与严重程度分级（高危/中危/低危）
   - 第三步：对每个风险特征调用`LongDocRetrievalSkill.retrieve()`进行交叉引用检索，验证判断一致性
   - 第四步：证据回溯验证，标记无原文支撑的推断为"低置信度"

2. **分级约束**：高危风险判定必须关联至少一条具体法律条款或监管规定引用（spec.md 5.2.1规则4）

3. **二次扫描机制**：当法律风险信息散布在非法律章节时，触发全文档二次扫描

### 1.3.3 FinanceAgent 财务穿透Agent

**设计要点**：

1. **分析流程**：
   - 第一步：调用`LongDocRetrievalSkill.retrieve()`检索财务报表段落
   - 第二步：调用vLLM进行标准化指标抽取与表内勾稽关系校验
   - 第三步：调用`CashFlowCalculationSkill`计算现金流消耗率与资金耗尽时间
   - 第四步：调用`PeerComparisonSkill`进行同行估值比对
   - 第五步：调用vLLM进行财务操纵特征识别
   - 第六步：综合至少两项以上交叉证据做出风险判定（spec.md 5.3.1规则5）

2. **财务指标校验**：表内勾稽关系验证、跨期连续性验证、同行横向对比异常检测

3. **现金流敏感性分析**：输出乐观/中性/悲观三组假设下的测算结果

### 1.3.4 SentimentAgent 市场情绪Agent

**设计要点**：

1. **分析流程**：
   - 第一步：从市场数据源获取大盘行情数据与板块流动性数据
   - 第二步：调用`SentimentScoringSkill`计算综合情绪热度评分（0-100分）
   - 第三步：调用vLLM进行舆情事件提取与影响评估
   - 第四步：按可配置时间间隔刷新情绪评分

2. **数据时效性保障**：核心市场数据时间戳距今不超过24小时，否则标记"数据过期预警"

3. **极端行情处理**：单日涨跌超5%触发极端行情模式，评分可靠度降级

### 1.3.5 LongDocRetrievalSkill 长文档检索Skill

**设计要点**：

1. **文档解析Pipeline**：
   ```
   PDF输入 → PyMuPDF文本提取 → 页码/章节映射 → 
   Unstructured语义分段 → 向量化(FAISS) → 元数据索引(Chroma)
   ```

2. **索引构建**：
   - 语义分片：基于段落边界与语义相似度的混合分片策略，每片目标长度512 tokens
   - 元数据标签：每片包含`page_number`、`chapter`、`section_type`（财务/法律/业务/风险等）
   - 向量化：调用vLLM的embedding接口生成向量表示

3. **检索策略**：
   - 向量相似度检索（FAISS Top-K）
   - 元数据过滤（按章节类型、页码范围）
   - 混合检索：向量检索 + 关键词BM25检索结果融合（RRF算法）

4. **幻觉抑制**：每个抽取结果附带原文片段引用与置信度标记，无原文支撑项标记为"低置信度"

### 1.3.6 PeerComparisonSkill 同行估值比对Skill

**设计要点**：

1. **输入**：发行人估值指标（PE/PB/PS/EV-EBITDA）+ 同行数据库查询参数
2. **处理**：从同行数据库获取可比公司数据，计算各指标的行业均值/中位数/标准差
3. **输出**：估值对比表，标注偏离同行均值的指标及偏离幅度（Z-Score）
4. **对标可靠度**：当可用可比公司少于3家时，标注"对标样本有限，结论可靠度降级"

### 1.3.7 CashFlowCalculationSkill 现金流消耗测算Skill

**设计要点**：

1. **计算逻辑**：
   - 现金流消耗率 = 经营性现金净流出 / 月份数
   - 资金耗尽时间 = 现金储备 / 现金流消耗率
   - 敏感性分析：在乐观/中性/悲观三组假设下分别计算

2. **输入**：经营性现金流数据、现金储备数据、假设条件参数
3. **输出**：现金流消耗率、预计资金耗尽时间（三种假设）、假设条件说明

### 1.3.8 SentimentScoringSkill 情绪热度打分Skill

**设计要点**：

1. **评分模型**：加权多因子模型
   ```
   情绪热度评分 = w1 × 大盘冷暖因子 + w2 × 板块流动性因子 + w3 × 舆情热度因子 + w4 × IPO认购倍数因子
   ```
   - 默认权重：`w1=0.3, w2=0.25, w3=0.25, w4=0.2`（可配置）
   - 大盘冷暖因子：基于指数走势、成交额变化、IPO首日涨跌统计映射至0-100
   - 板块流动性因子：基于日均成交额、换手率、资金净流入映射至0-100
   - 舆情热度因子：基于正负面新闻比例、社交媒体讨论量映射至0-100
   - IPO认购倍数因子：基于认购倍数映射至0-100

2. **输出**：综合评分（0-100）+ 各因子评分 + 因子贡献度分解

### 1.3.9 DebateProtocol 辩论协议

**设计要点**：

1. **辩论流程**：
   ```
   冲突检测 → 生成冲突描述 → 分发给相关Agent → 
   Agent补充证据/修正结论 → 一致性判定 → 
   [一致→结束 | 不一致→下一轮 | 3轮耗尽→不可调和冲突]
   ```

2. **一致性判定**：基于LLM辅助判断相关Agent的修正结论是否消除逻辑矛盾，判定标准为"矛盾方是否撤回或修正其原始结论使得不再存在逻辑冲突"

3. **不可调和冲突处理**：标记为"不可调和冲突"，附带各方论据摘要，触发人工审核流程

4. **辩论消息格式**：
   ```python
   class DebateMessage(BaseModel):
       round_id: int                    # 辩论轮次
       sender: AgentRole                # 发送方
       receiver: AgentRole              # 接收方
       conflict_id: str                 # 冲突标识
       conflict_description: str        # 冲突描述
       evidence: list[EvidenceRef]      # 补充证据
       revised_conclusion: Optional[str] # 修正结论
       stance: Literal["maintain", "revise", "concede"] # 立场
       timestamp: datetime              # 时间戳
   ```

### 1.3.10 CrossModalFusion 跨模态融合引擎

**设计要点**：

1. **特征对齐**：
   - 招股书基本面特征：低频、静态文本特征（法务风险等级、财务风险等级、风险特征计数）
   - 市场行情特征：高频、动态时序特征（情绪热度评分、大盘冷暖等级、板块流动性评级）
   - 对齐策略：将动态时序特征聚合为与基本面特征同维度的静态表示（取最新快照 + 趋势方向）

2. **融合策略**：加权融合
   ```
   综合风险评分 = α × 基本面风险评分 + β × 市场情绪风险评分
   ```
   - 默认权重：`α=0.65, β=0.35`（基本面为主，市场情绪为辅，可配置）
   - 基本面风险评分 = f(法务风险等级, 财务风险等级, 风险特征数量)
   - 市场情绪风险评分 = g(情绪热度评分, 大盘冷暖等级) — 注意：情绪极热本身构成风险因子

3. **综合风险评级映射**：
   | 综合风险评分区间 | 评级 |
   |----------------|------|
   | [0, 20) | 极低 |
   | [20, 40) | 低 |
   | [40, 60) | 中 |
   | [60, 80) | 高 |
   | [80, 100] | 极高 |

4. **可解释性**：输出中明确标注基本面因子与市场情绪因子的权重、各因子原始评分与贡献度

# **4. 数据模型**

## **4.1 设计目标**

1. **可追溯性**：所有分析结论必须可回溯至招股书原文页码，中间不得断链
2. **类型安全**：使用Pydantic V2进行严格类型校验，杜绝运行时类型错误
3. **标准化**：统一风险评级五级制、标准化财务指标命名、统一货币单位
4. **可扩展性**：支持新增Skill、新增Agent角色的数据模型扩展
5. **审计合规**：所有数据变更可追溯，支持按招股书ID/Agent角色/时间范围查询

    stance: Literal["maintain", "revise", "concede"]

class DebateRound(BaseModel):

### 4.2.7 持久化存储设计

| 数据实体 | 存储方案 | 说明 |
|----------|----------|------|
| ProspectusDocument | PostgreSQL | 招股书元数据与索引状态 |
| DocumentChunk向量 | FAISS索引文件 + Chroma | 向量检索与元数据过滤 |
| TraceRecord | PostgreSQL | 追踪审计记录，支持按ID/角色/时间查询 |

| RiskReport | PostgreSQL + 对象存储 | 报告元数据存PostgreSQL，完整报告JSON存对象存储 |
| AnalysisTask | PostgreSQL + Redis | 任务状态存PostgreSQL，实时进度存Redis |
| MarketData缓存 | Redis | 市场行情数据缓存，设置24小时TTL |
