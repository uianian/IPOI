## 1. 通用约定

### 1.1 统一响应格式

```json
// 成功
{ "success": true, "data": { ... } }

// 失败
{ "success": false, "error": { "code": "ERROR_CODE", "message": "人类可读描述" } }
```

### 1.2 HTTP 状态码

| 状态码 | 含义 | 场景 |
|--------|------|------|
| 200 | OK | 查询成功 |
| 202 | Accepted | 异步任务已接收（解析/分析启动） |
| 400 | Bad Request | 参数错误 |
| 404 | Not Found | 任务不存在或尚未完成 |
| 500 | Internal Server Error | 服务端异常 |

### 1.3 认证与跨域

- 认证：暂不强制；前端预留 `Authorization: Bearer <token>`
- 跨域：前后端不同域时需配置 CORS，允许 `Authorization` 头
- SSE 端点需支持 `text/event-stream`，建议 15s 心跳

### 1.4 `clientProjectId` 说明

路径参数与 `parse/expert/start` FormData 中的 `clientProjectId` 是**前端为每个项目生成的唯一编号**（如 `proj-a1b2c3d4`），即 `Project.id`，用于关联同一次解析/分析/报告请求。

- 创建规则：`proj-{Date.now().toString(16)}`；**每次创建项目都会生成新 ID**
- **即使上传同一份 PDF、同一 ticker，也会得到不同的 `clientProjectId`**（标识的是「这一次上传会话」，不是 PDF 内容哈希）
- **不是**后端数据库主键；后端**无需**实现项目 CRUD
- 可在内存/临时存储中按 `clientProjectId` + `taskId` 关联会话

### 1.5 可选 `llmConfig`（Agent 用大模型）

分析启动请求体可携带（用户在前端设置页配置，未配置则后端使用默认模型）：

```json
{
  "llmConfig": {
    "apiBaseUrl": "https://api.deepseek.com/v1",
    "apiKey": "sk-...",
    "model": "deepseek-chat"
  }
}
```

## 2. 接口清单（速查）

> 后端只需实现以下 **12 个接口**。项目管理不在此列。

| # | 方法 | 路径 | 说明 |
|---|------|------|------|
| 1 | GET | `/api/v1/health` | 健康检查 |
| 2 | GET | `/api/v1/agents/status` | Agent 集群状态 |
| 3 | POST | `/api/v1/parse/expert/start` | 上传+启动解析 |
| 4 | GET | `/api/v1/parse/expert/tasks/:taskId/progress` | 解析进度 |
| 5 | GET | `/api/v1/parse/expert/tasks/:taskId/result` | 解析结果 |
| 6 | GET | `/api/v1/projects/:clientProjectId/index-status` | 向量索引状态（解析后建索引；`ready` 后才可启动分析） |
| 7 | POST | `/api/v1/projects/:clientProjectId/analysis/start` | 启动多 Agent 分析（路径中 `clientProjectId` 即前端项目唯一编号） |
| 8 | GET | `/api/v1/projects/:clientProjectId/analysis/stream` | SSE Agent 思考流 + 辩论 |
| 9 | GET | `/api/v1/projects/:clientProjectId/analysis/result` | 已完成分析结果 |
| 10 | GET | `/api/v1/projects/:clientProjectId/report` | 风险报告 JSON |
| 11 | GET | `/api/v1/projects/:clientProjectId/report/export` | 报告 PDF 二进制 |

> **`clientProjectId`（项目唯一编号）**：前端每次创建项目生成新的 `proj-{hex}`；**同一 PDF 多次上传也会得到不同 ID**。详见 [§1.4](#14-clientprojectid-说明)。
> **索引门控**：解析完成后后端异步建向量索引；前端轮询 §6，仅当 `status=ready` 时才允许调用分析 start。

## 4. 项目管理（前端实现，无后端接口）

> **由前端实现。**

| 功能 | 实现方 | 说明 |
|------|--------|------|
| 项目列表 | 前端 | `localStorage` → `ipo:projects` |
| 创建项目 | 前端 | 生成 `proj-xxx`，缓存 PDF 到 IndexedDB |
| 查看/删除/导出/导入 | 前端 | 读写 IndexedDB `ipo-cache` |
| 报告下载 | 前端 | 读缓存 `report.pdf`（最新） |
| 重新分析 / 历史版本 | 前端 | 重跑前归档至 `analysis-history/`；主界面始终展示最新 |

### 4.1 前端本地缓存目录结构

```
ipo-cache/（IndexedDB）
├── projects.json 索引（实际在 localStorage）
└── projects/proj-xxx/
    ├── source.pdf
    ├── parse-content.md
    ├── parse-stats.json
    ├── analysis.json        ← 最新一次分析
    ├── report.json          ← 最新一次报告
    ├── report.pdf
    └── analysis-history/    ← 历史分析版本（重新分析时归档）
        ├── manifest.json
        └── {versionId}/
            ├── analysis.json
            ├── report.json
            └── report.pdf（可选）
```

### 4.2 Project 字段（供前后端对齐语义）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | `proj-{hex}`，即 `clientProjectId`（项目唯一编号；每次创建新项目生成，同一 PDF 多次上传亦不同） |
| `fileName` | string | 原始 PDF 文件名 |
| `projectName` | string? | **仅前端**；用户自定义项目名称，localStorage 存储，不参与任何 API |
| `ticker` | string | 港股代码，如 `9988.HK` |
| `parseMode` | `"expert"` | 前端恒为 `expert`（字段保留兼容旧本地数据） |
| `isBiotech` | boolean | 是否生物科技公司，上传时必选 |
| `enableEmbellishment` | boolean | 是否启用专业模式（文本粉饰度纳入评分）；上传弹窗「标准模式 / 专业模式」二选一，默认 `false`；随 `parse/start` 提交，后端保存至解析任务 |
| `uploadTime` | ISO 8601 | 创建时间 |
| `parseCompleteTime` | ISO 8601 \| null | 解析完成时间 |
| `status` | 见第 9 节 | 前端维护 |
| `parseProgress` | 0-100 | 解析进度 |
| `parseTaskId` | string? | 后端返回的解析 taskId |
| `parseDone` / `analysisDone` | boolean | 前端 flag |

## 5. PDF 解析

前端统一调用 `/parse/expert/*`。解析结果含 Markdown + 统计，**不含 images**。

### 5.1 `POST /api/v1/parse/expert/start`

```
Content-Type: multipart/form-data
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `file` | 是 | PDF 二进制 |
| `ticker` | 是 | Wind 格式港股代码字符串，如 `9988.HK`；前端无论用户输入 Wind 代码（`0084.HK`）或股票代码（`0084`），提交时均规范化为 Wind 格式 |
| `clientProjectId` | 是 | **项目唯一编号**，格式 `proj-{hex}`，与 `Project.id` 一致；每次创建项目生成新值，**同一 PDF 多次上传也会不同**（见 §1.4） |
| `fileName` | 是 | 原始文件名 |
| `isBiotech` | 是 | `"true"` / `"false"`，是否生物科技公司；前端创建项目时选择，随 PDF 提交；后端应保存至解析任务，供 Agent 分析使用 |
| `enableEmbellishment` | 是 | `"true"` / `"false"`，是否启用专业模式（文本粉饰度纳入评分）；前端上传弹窗「标准模式 / 专业模式」二选一，默认 `"false"`；随 PDF 提交；后端应保存至解析任务，供 Agent 分析使用 |
| `companyName` | 否 | 公司中文名称；来自前端 `company-lookup.json`；lookup 未命中传空字符串 `""` |
| `listDate` | 否 | 上市日期；同上，格式与 xlsx 一致（如 `2020-01-01`）；未命中传 `""` |

**响应 202**：

```json
{
  "success": true,
  "data": {
    "taskId": "task_expert_20260810_001",
    "status": "parsing"
  }
}
```

### 5.2 `GET /api/v1/parse/expert/tasks/:taskId/progress`

前端每 **500ms** 轮询。

```json
{
  "success": true,
  "data": { "progress": 67, "stage": "PARSING" }
}
```

| stage | 含义 |
|-------|------|
| `PARSING` | 解析中 |
| `READY` | 完成（且 progress=100） |

### 5.3 `GET /api/v1/parse/expert/tasks/:taskId/result`

**响应 200**：

**必填字段**：`taskId`、`projectId`、`mode`、`status`、`stats`、`markdown`

> `markdown` 为 **Markdown 与 HTML 混排**字符串（表格等可为 HTML 片段）；前端使用 Streamdown（含 rehype-raw）渲染为「文档预览」，后端无需额外字段。

**可选字段**：`companyInfo`（前端已用 Wind lookup 展示公司信息，后端可不返）、`completedAt`

```json
{
  "success": true,
  "data": {
    "taskId": "task_expert_20260810_001",
    "projectId": "proj-a1b2c3d4",
    "mode": "expert",
    "status": "completed",
    "stats": {
      "totalPages": 250,
      "parsedPages": 250,
      "chartCount": 0,
      "tableCount": 42,
      "textChunkCount": 0
    },
    "markdown": "# 招股书正文\n\n...",
    "companyInfo": {
      "companyName": "示例公司",
      "ticker": "9988.HK",
      "industry": "电子商务"
    },
    "completedAt": "2026-08-10T10:42:30Z"
  }
}
```

> `companyInfo` 为可选。最小响应只需必填字段六项；公司信息卡片由前端 `company-lookup.json` 按 ticker 匹配。

**禁止返回**：`images`、`chunk JSON`、原始表格结构、`pdfUrl`、PDF 二进制。

未完成 → **404**，`error.code`: `PARSE_NOT_COMPLETED`

## 6. 向量索引状态

解析返回结果后，后端需对招股书内容建立向量索引（可能需数分钟）。**多 Agent 分析依赖索引就绪**；前端在分析页轮询本接口，未 `ready` 时点击「启动分析」仅提示等待，不调用 `analysis/start`。

### `GET /api/v1/projects/:clientProjectId/index-status`

**Query（可选）**：

| 参数 | 说明 |
|------|------|
| `taskId` | 解析任务 ID；有则优先按任务查询，无则按 `clientProjectId` |

**响应 200**：

```json
{
  "success": true,
  "data": {
    "status": "indexing",
    "message": "向量索引构建中",
    "progress": 40
  }
}
```

| `status` | 含义 | 前端行为 |
|----------|------|----------|
| `indexing` | 建索引中 | 每 3s 继续轮询；点分析按钮 → toast「索引建立中，还需要等几分钟，请稍后」 |
| `ready` | 索引完成 | 停止轮询；允许启动分析 |
| `failed` | 建索引失败 | 停止轮询；toast 错误提示 |

- `progress`（0–100）、`message` 可选，用于按钮旁弱提示
- 未找到对应项目/任务 → **404**，`error.code`: `INDEX_STATUS_NOT_FOUND`

## 7. 多 Agent 分析

### 7.1 `POST /api/v1/projects/:clientProjectId/analysis/start`

**请求体**：

```json
{
  "clientProjectId": "proj-a1b2c3d4",
  "taskId": "task_expert_20260810_001",
  "llmConfig": { "apiBaseUrl": "...", "apiKey": "...", "model": "..." }
}
```

- `clientProjectId`：与路径参数一致（前端会重复传，便于日志）
- `taskId`：可选，关联本次 PDF 解析任务
- `llmConfig`：可选，缺省用后端默认大模型
- `isBiotech`：可选；若后端已在解析任务（`parse/start`）中保存，分析启动时可不再要求；否则 body 中传 `isBiotech: true/false`
- `enableEmbellishment`：可选；若后端已在解析任务（`parse/start`）中保存，分析启动时可不再要求；否则 body 中传 `enableEmbellishment: true/false`。`false` = 标准模式（不纳入文本粉饰度评分）；`true` = 专业模式（纳入文本粉饰度分析，Token/费用更高）

**响应 202**：

```json
{
  "success": true,
  "data": {
    "analysisId": "analysis_20260722_001",
    "status": "started"
  }
}
```

### 7.2 `GET /api/v1/projects/:clientProjectId/analysis/stream`

`Content-Type: text/event-stream`，建议 15s `heartbeat`。

| 事件 | 说明 |
|------|------|
| `agent_status` | `{"agentId":"legal","status":"running"}` |
| `thought` | `{"thought":{ "id","agentId","type","content","ref?","timestamp","meta?" }}` |
| `phase_change` | `{"phase":"debate","message":"三位专家已完成初评，进入辩论环节"}` |
| `agent_report` | `{"agentId":"legal","reportMarkdown":"...","agentResult":{...}}` |
| `debate_message` | `{"message":{ "id","agentId","round","type","content","targetAgentId?","timestamp" }}` |
| `debate_complete` | `{"rounds":3}` |
| `report_ready` | `{"report":{ /* ReportData */ }}` |
| `analysis_complete` | `{"overallScore":75,"riskLevel":"HIGH"}` |
| `heartbeat` | `{"timestamp":...}` |

`thought.type`：`thinking` | `finding` | `conclusion`

**`thought.meta`（可选，Agent 扩展）**：

| 字段 | 说明 |
|------|------|
| `kind` | `tool_call` / `tool_result` / `model_think` / `risk_point` / `evidence` 等 |
| `toolName` | 工具名，如 `retrieve_legal` |
| `toolStatus` | `running` / `ok` / `error` |
| `evidence` | 证据数组，见下表 |
| `rawThink` | 模型原始推理文本（可选） |

**`meta.evidence[]` 元素**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `page` | number | PDF 页码 |
| `excerpt` | string | 原文摘录 |
| `sourceType` | string | 如 `text` / `table` |
| `fieldCode` | string? | 风险字段码，如 `RELATED_PARTY` |
| `sectionId` | string? | 章节标识 |
| `confidence` | number? | 检索置信度 |

前端摘要模式：`finding` 展示 `meta.evidence` 按页分组；`tool_call` / `tool_result` 类 `thinking` 默认隐藏。

Agent 顺序：`legal` ∥ `financial` ∥ `market` → `agent_report` ×3 → **debate**（四 Agent 轮流发言）→ `orchestrator` 生成 `report` → `analysis_complete`

**辩论过程展示（双通道）**：

- **进行中**：前端依赖 `debate_message` SSE 逐条展示；`analysis/result.debate.messages` 为快照，进行中可只含已产生部分。
- **完成后**：`analysis/result` 返回完整 `debate` 与 `agents` 树。

刷新页面时前端可拉取完整历史（也可只依赖本地缓存）。进行中也可返回部分 `thoughts`、`agents.*`、`debate.messages`。

## 8. 风险报告

### 8.1 `GET /api/v1/projects/:clientProjectId/report`

返回报告 JSON（字段名须与前端 `ReportData` 一致，见 `client/src/data/reportData.ts`）。

关键字段：`overallScore`、`riskLevel`、`riskLabel`、`dimensions`、`riskFactors`、`comparableIPOs`、`riskTimeline`、`radarData`

可选扩展：`executiveSummary`（Markdown 摘要）、`debateHighlights`（辩论要点）、`agentScores`（各 Agent 分数）

> 与 `analysis/result.report` 结构相同。前端会在分析完成后调用一次并**缓存到 IndexedDB**，之后查看/下载不再依赖后端。

### 8.2 `GET /api/v1/projects/:clientProjectId/report/export`

```
Content-Type: application/pdf
Content-Disposition: attachment; filename="IPO风险报告_9988.HK_2026-07-22.pdf"
```

返回 PDF 二进制；前端缓存为 `report.pdf` 供下载。

## 9. 项目状态与数据类型

### 9.1 状态（前端维护）

| status | 含义 | 触发 |
|--------|------|------|
| `uploading` | 上传中 | 创建项目 |
| `parsing` | 解析中/已解析 | 进入解析页、解析完成 |
| `analyzing` | 分析中 | 启动 Agent 分析 |
| `completed` | 已完成 | 分析完成 |

后端**不需要**更新上述 status 字段。

### 9.2 ParseResult（`/result` 响应）

```typescript
interface ParseResult {
  taskId: string;
  projectId: string;       // clientProjectId
  mode: "expert";
  status: "completed" | "failed";
  stats: ParseStats;
  markdown: string;
  companyInfo?: CompanyInfo; // 可选，展示由前端 Wind lookup 负责
  completedAt?: string;
}

interface ParseStats {
  totalPages: number;
  parsedPages: number;
  chartCount: number;
  tableCount: number;
  textChunkCount: number;
}
```

### 9.3 Thought

```typescript
type AgentId = "legal" | "financial" | "market" | "orchestrator";

interface ThoughtEvidence {
  page: number;
  excerpt: string;
  sourceType?: string;
  fieldCode?: string | null;
  sectionId?: string | null;
  confidence?: number;
}
```

### 9.5 公司信息查询（无后端接口）

前端通过静态文件 `client/public/company-lookup.json` 按 ticker 查询并展示「公司信息」卡片（`BasicInfoCard`）。

**数据源**：`data/companyinfo.xlsx`（中文表头）→ `pnpm build:data` → `client/public/company-lookup.json`

**查询规则**：

- 用户上传时可输入 **Wind 代码**（如 `0084.HK`）或 **股票代码**（如 `0084`、`84`）
- JSON 以 Wind 代码为 `records` 主键，并建立 `aliases` 索引支持股票代码反查
- 1～4 位纯数字左补零至 4 位；5 位代码（如 `80016`）保持 5 位不截断

**提交后端 ticker 格式**：

- 写入 `Project.ticker` 与 `parse/start` FormData 的 `ticker` 字段时，**一律为 Wind 格式字符串**（带 `.HK` 后缀，如 `0084.HK`）
- lookup 命中时使用 `record.windCode`；未命中时按 `normalizeWindCode` 规则规范化

**提交后端公司信息**（`parse/expert/start` FormData）：

- lookup 命中时附带 `companyName`（公司中文名称）、`listDate`（上市日期）
- 未命中时两字段传空字符串 `""`
- 上述字段由前端 Wind lookup 提供，**不是**后端 `/result` 返回

**卡片展示字段**（来自 xlsx，共 6 项）：公司中文名称、公司英文名称、证券简称、上市日期、上市板、注册地所在国家或地区。

- **后端 `/result` 无需返回 `companyInfo`**；若返回，仅作 Wind 查不到时的标题兜底
- `CompanyInfo.industry` 等字段不由后端维护
